# Giper Baza explain

Под постом про [Blitz Quiz](https://b-on-g.github.io/blitz/) спросили: выглядит круто, а как эта ваша гипербаза работает? Кроме тг-канала почитать про неё особо негде. Справедливый упрёк, исправляюсь)

Короткий ответ: для разработчика это что-то типа ОРМ как в джанге. Описываешь модель данных и используешь её. Но под капотом оно ещё само синкается! Причём бесконфликтно.

Вот модель квиза из Blitz Quiz, целиком:

```ts
export class $bog_blitz_quiz extends $giper_baza_dict.with({
	Title: $giper_baza_atom_text,
	Questions: $giper_baza_list_link_to( ()=> $bog_blitz_question ),
	Time_read: $giper_baza_atom_real,
	Time_answer: $giper_baza_atom_real,
	Time_leaderboard: $giper_baza_atom_real,
	Time_reveal: $giper_baza_atom_real,
	Points_base: $giper_baza_atom_real,
	Time_multiplier: $giper_baza_atom_real,
	Manual_mode: $giper_baza_atom_bool,
}) {}
```

Читаешь поле так: `quiz.Title()?.val()`. Пишешь так: `quiz.Title('auto')?.val('Столицы мира')`. На этом взаимодействие с базой заканчивается. Ни ручек на сервере, ни кода синхронизации писать не нужно.

Философия в том, что мы как будто работаем с локальной базой. Синк реализован под капотом, задумываться о нём не нужно, как и о примитивах синхронизации. В моле это сделано заранее: поле поменялось локально или прилетело с другого устройства, для твоего кода разницы нет, интерфейс просто перерисовывается.

Теперь куда оно синкается. На серверах крутятся такие же ноды синхронизации, как у клиентов. При этом на сервере не происходит расшифровка. Никогда, даже при мерже: нода мержит чужие зашифрованные изменения, не зная, что внутри. Мерж бесконфликтный, через CRDT. Тут есть прикол: у половины решений, которые заявляют CRDT, при реальном использовании вылезают косяки, по типу очень быстрого роста базы. Есть [известный замер](https://josephg.com/blog/crdts-go-brrr/): трейс из 260 тысяч правок текста, итоговый документ 100 тысяч символов. Automerge жевал его 291 секунду и съел 880 МБ памяти, Yjs тот же трейс прошёл за секунду и 3.3 МБ. Авторы с тех пор много починили, но в [релизе Automerge 3](https://automerge.org/blog/automerge-3/) сами пишут: вставка «Моби Дика» в документ ела 700 МБ памяти, стало 1.3 МБ. У Yjs своя особенность: документ умеет только расти, удалённый контент оставляет надгробия, и даже «удаление истории» делает файл больше. В [гайде Liveblocks](https://liveblocks.io/docs/guides/why-you-cant-delete-yjs-documents) приводят боевые документы по 5 МБ при контенте в 75 КБ. В Гипер Базе куча таких нюансов и мелочей решена. Разбор конкурентов с бенчами тянет на отдельную статью, а за внутренностями отправляю к первоисточнику: у Димы Карловского есть [«Революция архитектуры Веба»](https://habr.com/ru/articles/943606/) и [«Что если… ( безумные идеи хранения данных )»](https://habr.com/ru/articles/956154/).

Шифрование при этом не тотальное, можно делать и незашифрованные блоки, открытая база читается любым желающим.

Права живут на уровне самой базы, приложение их не изобретает. Уровней пять: deny ( доступа нет вообще ), read, post ( можно постить изменения ), pull ( можно вливать форки ) и rule ( полный контроль, включая раздачу прав другим ). Владелец базы всегда rule, остальным права выдаются персонально или дефолтом для всех.

А вторая ось прав решает проблему ботов. Нам не важно, бот к нам пришёл или человек: пока процессор не подберёт запись с определённым количеством единичек, запись не уйдёт на сохранение. Это proof of work, и его сложность зашита в те же права: чем меньше тебе доверяют, тем дороже писать, от микросекунд работы CPU до дней. Ботоферма становится экономически невыгодной просто за счёт PoW, капча не нужна.

В квизе это всё видно живьём: у каждого игрока своя база с его ответами, куда чужие писать не могут, а в общей сессии лежит только ссылка на неё. Хост читает базы игроков и считает очки, никто никому не мешает. Нюансов недоделанных в квизе ещё много, но возможности показывает)

Теперь про грабли, на которые я наступил сам. Первая запись файла или создание новой базы требует того самого proof of work. Считается он внутри wire-задачи мола, и результат кешируется только в пределах одной фибры. Я запускал сохранение файлов из обычной async-функции, и получалось так: запись бросает Promise ( PoW ещё не готов ), async-функция ретраится с начала, сохранение запускается с нуля и заводит новый PoW-таск. И так по кругу: каждый заход 1-10 секунд работы CPU, main thread занят, UI висит, в логах бесконечные «start … ensure file land» без прогресса. Лечится одной строчкой: запись оборачивается в `$mol_wire_async(this).save_in_fiber(...)`. Внутри фибры подзадачи кешируются, и при ретрае она получает уже посчитанный PoW вместо нового.

Чего пока нет, так это файлового сервера. Файлы можно грузить в саму базу, но показать их могут только приложения, которые эту базу читают. Просто скопировать ссылку на файл и переслать не выйдет, не откроется. Я хотел сделать себе блог с визивиг-редактором, чтобы он выступал источником истины, а я оттуда копировал контент во все другие места, но пока не вышло. ПР с файловым сервером в Гипер Базу уже есть, поддержать это несложно.

Ещё из заложенного архитектурно: можно поднять свою подсеть из гипер баз, это предусмотрено и со стороны приложений, и со стороны кода Гипер Базы для развёртывания.
